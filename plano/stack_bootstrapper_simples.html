Gestão de usuários — sem complicação
O fluxo completo de "alguém compra → ganha acesso → usa o app → cancela" funciona com ferramentas que já existem. Você não precisa escrever um sistema de autenticação do zero.
1
Cliente compra no Hotmart
Automático
→
Hotmart dispara um webhook para o seu app. Webhook é um aviso automático: "fulano@email.com comprou o plano Regional."
→
Seu app recebe esse aviso, cria o usuário no SQLite com e-mail + senha temporária + tier "regional".
→
Brevo dispara e-mail: "Seu acesso foi criado. Login: fulano@email.com / Senha: XXXX. Acesse aqui: seuapp.com"
2
Cliente entra no app e usa
Automático
→
Tela de login: digita e-mail e senha. App verifica no SQLite. Se ok, entra.
→
App lê o tier do usuário. Tier "operacional" → vê filtros e pode baixar até 300 leads/mês. Botão de download some quando atinge o limite.
→
Tier "explorador" → vê tudo mas o botão de download mostra: "Faça upgrade para baixar."
3
Notificações automáticas que retêm
Automático via Brevo
📬
Segunda-feira, 08h: "Esta semana, 127 novas empresas de beleza abriram no seu estado. Acesse para ver quais."
📬
Quando usa 80% dos exports: "Você já usou 240 dos seus 300 exports este mês. Quer mais? Upgrade para Regional."
📬
5 dias antes de expirar: "Seu plano vence em 5 dias. Renove agora e continue acessando X novas empresas por semana."
4
Cancelamento / expiração
Automático
→
Hotmart webhook avisa: "fulano cancelou." App muda o tier para "expirado". Login ainda funciona mas download bloqueado.
→
Brevo dispara e-mail de winback: "Sentimos sua falta. Esta semana X novos salões abriram no seu estado. Reative com 20% OFF."
Você gerencia como? Você tem um Google Sheets simples (ou Notion) onde você vê: usuários ativos, tier de cada um, data de expiração. Isso é o seu "painel de controle" como solo founder. Não precisa de dashboard sofisticado — uma planilha resolve.
Segurança e LGPD — menos assustador do que parece
A grande maioria das preocupações de segurança não se aplica ao seu produto. Entenda por quê, e o que você precisa fazer de verdade.
🛡️
O que Railway faz por você
✅
HTTPS/SSL automático — toda comunicação criptografada. Nada trafega em texto aberto.
✅
Firewall e isolamento — cada app roda isolado. Ninguém acessa seu servidor.
✅
Backups automáticos — Railway faz snapshot do volume de dados.
✅
Infraestrutura na AWS — mesma base que grandes empresas usam.
🔐
O que você precisa fazer no código
✅
Senhas criptografadas com bcrypt — biblioteca Python, 3 linhas de código. Nunca armazena senha em texto.
✅
Session token — usuário logado recebe um token. Se fechar o navegador, precisa logar de novo.
✅
Nada mais. É um app de consulta de dados públicos, não um banco.
⚖️
LGPD — por que é simples no seu caso
✅
Dados de CNPJ são dados PÚBLICOS da Receita Federal. A LGPD protege dados pessoais (CPF, nome, endereço residencial). CNPJ empresarial não é dado pessoal — é registro público.
✅
Você não armazena CPF de ninguém. Você armazena CNPJ, razão social, telefone empresarial — todos dados da Receita Federal, públicos por lei.
✅
Dados dos seus clientes (usuários do app): e-mail + senha. Esses você protege com criptografia (bcrypt) e não compartilha com ninguém. Isso é suficiente.
⚠️
O que você precisa ter: Política de Privacidade na landing page (pode ser gerada com gerador gratuito online) e Termos de Uso. Uma tarde de trabalho.
Resumo de segurança para um solo founder: Railway cuida do servidor. bcrypt cuida das senhas. Hotmart cuida do pagamento. Brevo cuida do e-mail. Você não toca em cartão de crédito, não armazena CPF, não processa dado sensível. O risco é mínimo e proporcional ao tamanho do negócio. Não precisa de DPO nem de consultor jurídico agora.
